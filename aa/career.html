개발 Harness 구축·실제 프로젝트 적용

신규 프로젝트는 PRD를 분석해 프로젝트별 Harness를 구축하는 것부터 시작했습니다. 분석 결과로 Technical Spec·ADR을 작성하고, WBS와 CPM 분석을 바탕으로 실행할 Task를 Markdown으로 정리했습니다. 구현의 기준이 되는 분석·설계·WBS·CPM·Task 문서는 도출 후 직접 검수했습니다.

이후 구현은 Implementer, 검증은 별도의 리뷰 Sub-agent가 담당하도록 구성했습니다. 이 역할 분리에 따라 구현·리뷰·QA를 자동 수행하도록 했습니다. Orchestrator는 단계별 리뷰를 진행하고 문제가 있으면 이전 단계로 돌아가도록 구성했습니다.

수행 결과는 Report로 남겨 사후 점검했습니다. Report에서 문제를 발견하면 재작업을 요청해 Harness Workflow가 다시 실행되도록 했습니다.

Development Context에 아키텍처 원칙을 명시해 개발 기준을 제공했습니다. 모든 작업이 완료되면 Harness 자체의 개선사항을 도출하고 개선 작업을 수행하도록 Feedback Loop를 구성했습니다.

AI 도입 이전에 개발한 프로젝트는 기존 구조를 분석해 Harness를 구축했습니다. 균일한 품질을 위한 Development Context와 QA·리뷰용 Skill·Agent를 구성했습니다. 기술부채를 주간 단위로 분석하고 개선 과제를 도출하는 Agent도 구축했습니다.

Spec Driven Development 적용 사례: 제휴 API 연동

신규·기존 프로젝트의 Harness에는 문서 직접 검수, 구현·리뷰·QA 자동 수행, Report 사후 점검의 공통 운영 구조를 적용했습니다. 제휴 API 연동도 이 Harness를 적용해 구축했습니다.

작업 규모에 따라 Task 분석 또는 ADR을 포함한 Technical Spec을 작성하도록 했습니다. 제휴 연동에서는 API 명세·Mapping Table·Test Guide를 정형화하고 AI가 구현할 책임을 Adapter 단위로 제한했습니다. 내부 서비스는 SDK Connector의 통일된 인터페이스를 사용하도록 설계했습니다.

동일한 제휴 기능을 연동하는 데 주문 영역에서 개발해야 하는 서비스를 3~4개에서 1개로 줄였습니다. 기존에는 주문 영역에서 개발자 2~3명이 필요했지만, 변경 후에는 1인 개발이 가능해졌습니다. 제휴사 1곳의 설계 착수부터 QA 완료까지 걸리는 기간은 약 2개월에서 약 2주로 단축했습니다.

개발실 업무 분석 Agent·앱 구축

개발 실장으로서 구성원의 업무와 리소스 투입 현황을 파악하기 위해 AI Agent를 구성하고 같은 기능의 앱을 직접 개발했습니다.

  • Jira에서 구성원의 업무 현황과 리소스를 파악했습니다. Label로 업무 유형을 분류하고 구성원별 투입 현황과 실 전체의 업무 비중을 분석했습니다.
  • GitHub PR에서 구성원이 수행한 작업과 리뷰 활동을 파악했습니다.
  • Slack·Confluence에서 구성원들의 업무와 관련 커뮤니케이션을 분석했습니다.

분석 결과로 Daily·Weekly Report를 작성하고 HTML로 생성해 조직 내에 공유했습니다. AI Agent는 매주 월요일 오전 8시에 실행하도록 예약했으며, 직접 개발한 앱도 업무 파악에 활용했습니다.

서비스 카탈로그 제작·공유

AI가 코드 저장소와 관련 문서를 분석하도록 구성해 프로젝트의 용도, 기술 스택, 배포 파이프라인과 서비스 구조를 문서화했습니다. 문서 없이 코드만 남은 프로젝트는 코드를 분석 근거로 사용했습니다.

운영 중인 AWS 환경은 CLI로 토폴로지를 분석하고 시각화했습니다. 분석 내용을 서비스 카탈로그로 정리하고 Markdown을 기준 원본(Source of Truth)으로 관리했습니다. GitHub Pages로 조직에 공유하고, 필요할 때 직접 AI에 재분석을 요청해 카탈로그를 갱신했습니다.

티켓팅 주문 플랫폼 통합

기간·역할: 2023.09–2024.08 · 아키텍트·TF 리더 · 기획·개발 7명

디바이스, 장르, 자체·제휴 채널과 국내·글로벌 언어별로 11개 시스템이 분리되어 있었습니다. 같은 요구사항을 여러 소스에 반복 반영해야 했으며, Classic ASP·.NET Framework·MS-SQL·Stored Procedure에 축적된 업무 규칙을 운영과 함께 전환해야 했습니다.

본인 수행

  • 공통 기능과 정책 차이를 분석하고, 채널·디바이스 차이를 설정과 정책으로 처리하는 단일 플랫폼의 경계를 설계했습니다.
  • 좌석 없는 전시 상품부터 전환하는 순서를 정하고 프로덕트 조직과 상품별 적용 범위·신구 시스템 병행 방식을 조율했습니다.
  • 부하가 집중되는 좌석 데이터를 AWS DocumentDB로 분리하고 캐시를 적용했습니다. 좌석도는 래스터에서 벡터 방식으로 변경했습니다.
  • Stored Procedure의 비즈니스 로직을 Java·Kotlin 애플리케이션 계층으로 이동하고, 결제 완료 이후 주문 생성에 Kafka 이벤트를 적용했습니다.
  • Next.js·React·Java·Kotlin·AWS ECS 기반 서비스의 핵심 구현과 리뷰에 참여했습니다.

프로젝트 결과

11개 시스템을 단일 플랫폼으로 통합했습니다. 2026-09-22 기준, 공연·전시·스포츠를 포함한 전체 티켓팅 판매 상품의 약 95%가 신규 플랫폼에서 판매되고 있습니다. 기존에는 동일 요구사항을 11개 시스템에 각각 개발·반영해야 했지만, 단일 소스로 통합한 뒤에는 1개 서비스만 변경하도록 개발 범위를 줄였습니다. 개별 서비스 배포는 약 1~2분, 전체 컨테이너 교체는 약 5분으로 개선했습니다.

PDP·BFF·운영환경 현대화

기간·역할: 2022.04–2024.10 · FE개발팀장 · 조직 5명

React 정적 파일과 Java API가 같은 WAS에서 제공되고, EC2별 Docker 컨테이너를 Shell Script로 배포했습니다. 대기열 보호가 없는 PDP에 공연 판매 트래픽이 직접 유입되어 수분에서 수시간의 장애가 반복되었습니다.

Spring MVC·JDK 11 기반의 PDP 노출용 데이터 조회 API는 여러 백엔드 API를 직접 호출해 FE에 필요한 데이터를 조합했습니다. 대용량 트래픽이 유입되면 백엔드 호출이 동시에 늘어나고, 동기식 처리로 지연이 누적되었습니다.

본인 수행

  • 정적 자산을 CloudFront·S3로 분리하고 컨테이너 운영을 ECS·Auto Scaling으로 전환했습니다.
  • API를 단순 전달하던 구조를 화면에 필요한 데이터를 조합·가공하는 BFF로 재설계했습니다.
  • 인증 직후 예매에 사용하는 선예매 인증 정보는 실시간 조회를 유지했습니다. 공연정보·캐스팅 등 메타데이터에는 캐시를 적용했습니다.
  • 상품 정보 변경이 가능한 평시에는 TTL을 5분으로 설정했습니다. 정보가 변경되지 않는 대형 공연 판매 직전·판매 중에는 TTL을 1시간으로 늘렸습니다. 정책은 상품 오픈 시간에 맞춰 자동 적용했습니다.
  • 다수의 백엔드 API 호출을 CompletableFuture로 비동기 처리했습니다. CompletableFuture.allOf로 호출 완료를 기다린 뒤 결과를 조합해 응답을 만들었습니다.
  • 변경이 적은 데이터를 별도 저장소에 사전 정제하고 변경 빈도에 맞춘 캐시 정책을 적용해 레거시 DB 접근을 줄였습니다.
  • 불필요한 객체 생성과 GC 부담이 큰 로직을 정리하고 메모리 사용 방식을 개선했습니다.
  • 메인·랭킹·검색을 Next.js로 전환하고 서비스 특성에 따라 SSR·CSR을 구분했습니다.
  • 공통 모듈과 리뷰 기준을 제공하고, 구성원의 경험에 따라 Java·Spring 업무를 단계적으로 배분했습니다.

프로젝트 결과

PDP 노출용 데이터 조회 API의 대용량 트래픽 유입 시 평균 API 응답시간을 3~5초에서 1초 이내로 단축했습니다. 플랫폼 개선을 통해 대형 공연 판매 시 반복되던 PDP 장애도 해소했습니다. 팀 전원이 React와 Java·Spring BFF를 함께 개발·운영하는 형태로 전환했습니다.

최대 12명 규모의 주문 개발 조직에서 대기열·인증 게이트·좌석 선택·주문·결제·예매 완료의 기술 방향과 운영 안정성을 담당했습니다. 설계·핵심 개발을 병행하며 두 팀의 역할, 코드 리뷰와 협업 기준을 정리했습니다. 운영·사업 과제와 기술부채의 우선순위를 조정할 때 장애 위험과 개발 여력을 함께 설명했습니다.

Vue.js 기반 Back Office 개발

Back Office 화면을 Vue.js로 개발해 항공 업무 데이터와 운영 기능을 연결했습니다. 백엔드 API와 화면 흐름을 함께 설계·구현해 운영자가 필요한 정보를 확인하고 후속 처리를 수행할 수 있도록 했습니다.

웹메일 성능 개선과 제품화

외부 SI로 개발된 웹메일은 목록 조회 API의 지연으로 납품이 어려웠습니다. 메일이 적으면 1~2초 내 응답했지만, 메일 수가 늘어날수록 지연이 증가해 약 100개일 때 약 30초가 걸렸습니다. Java IMAP 라이브러리의 동기화·순차 처리 병목을 확인하고 메일 서버 내부에서 조회용 데이터를 제공하도록 구조를 바꿨습니다.

  • Dovecot Plugin Interface를 사용하는 C 플러그인을 개발해 필요한 데이터를 별도 DB에 적재했습니다.
  • 웹 애플리케이션이 DB에 직접 접근하지 않도록 내부 API를 구성했습니다.
  • 대량 조회를 병렬 처리하고 메일 발송을 메시지 큐 기반 비동기 처리로 분리했습니다.

개선 후 측정에서는 메일 수량에 관계없이 목록 조회 API가 1초 이내로 응답했습니다. 제품은 약 3개 고객사에 적용되었습니다. 프론트엔드는 기존 그룹웨어의 jQuery를 유지하되, 페이지별 필요한 모듈을 pre-load하는 모듈 선언·Lazy Loader와 모듈 기준의 trigger·function 바인딩 규칙을 정리해 팀에 전파했습니다.
