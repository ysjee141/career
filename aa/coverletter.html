개발을 좋아하고, 배운 것을 실제로 동작하게 만드는 아키텍트

저는 개발과 기술을 좋아합니다. 새로운 기술이 나오면 개념을 읽는 데서 멈추지 않고 PoC나 토이 프로젝트로 직접 적용해 보며, 실제로 동작하는 구조와 아직 해결되지 않은 한계를 확인합니다. 아키텍처도 서적과 실무 사례를 통해 꾸준히 학습하고, 배운 원칙이 현재 시스템의 문제를 해결하는 데 도움이 되는지 검토한 뒤 업무에 적용해 왔습니다.

개인 프로젝트에서도 AI를 활용해 앱을 개발하며 새로운 기술을 직접 적용해 봅니다. 다양한 도메인과 기술 경험을 새로운 문제에 적용하고, 설계한 구조가 실제로 동작하는 것을 확인하는 과정에서 즐거움을 느낍니다. 실무에서는 프로젝트별 개발 Harness와 명세 기반 개발을 적용하고, 구현 결과를 리뷰·QA와 사후 점검으로 확인하는 체계를 구축했습니다.

운영 중인 서비스를 이해하고, 실제로 바꾸는 아키텍트

저는 새로운 도메인의 업무 규칙과 운영 제약을 빠르게 이해하고, 그 제약 안에서 실제로 동작하는 애플리케이션 구조를 설계해 온 개발자입니다. 공장자동화에서 시작해 웹 솔루션, 그룹웨어, 웹메일, 항공 OTA, 티켓팅으로 경험한 도메인을 넓혀 왔습니다. 도메인이 바뀔 때마다 기존 시스템의 책임과 데이터 흐름을 먼저 파악하고, 문제의 원인이 있는 계층까지 내려가 필요한 구조를 바꾸는 방식으로 일했습니다.

아키텍처를 문서로만 정의하지 않습니다. 설계한 경계를 핵심 코드와 리뷰 기준으로 연결하고, 운영 중인 서비스에 단계적으로 적용합니다. 서비스가 멈추지 않아야 하는 상황에서는 전환 순서와 영향 범위를 나누고, 팀이 지속적으로 변경할 수 있도록 공통 모듈과 개발 기준을 함께 정리합니다.

백엔드를 전문으로 하지만 솔루션을 완성하기 위해 프론트엔드와 인프라, 배포 환경까지 직접 다뤄 왔습니다. 코비젼에서는 웹메일 백엔드·메일 서버와 함께 jQuery 프론트엔드를 화면 단위 모듈과 Lazy Loader 구조로 정비하고, 모듈 기준의 trigger·function 바인딩 규칙을 팀에 전파했습니다. 굿센에서는 AngularJS로 신규 서비스의 프론트엔드 전체를 구축해 웹메일을 포함한 서비스를 출시했고, 타이드스퀘어에서는 Vue.js 기반 Back Office를 개발했습니다.

놀유니버스에서는 React 기반 PDP 정적 자산을 Java WAS에서 CloudFront·S3로 분리하고, EC2 기반 서비스를 ECS로 재구축했습니다. 이후 신규 프로젝트에는 Next.js를 도입해 표준으로 정착시켰습니다. AWS 기반 인프라 설계, GitHub 브랜치 전략 수립, CI/CD 표준화까지 연결해 개발한 솔루션이 배포되고 운영되는 전체 흐름을 다뤄 왔습니다.

레거시와 대용량 트래픽 문제를 구조적으로 개선한 경험

놀유니버스에서는 장르·디바이스·채널·언어별로 나뉘어 있던 11개 티켓팅 시스템을 단일 플랫폼으로 통합하는 TF의 아키텍트·리더로 참여했습니다. 기존 시스템에는 오랜 기간 축적된 업무 규칙과 Stored Procedure가 있었고, 판매를 중단하지 않은 상태에서 상품별로 전환해야 했습니다.

저는 공통 기능과 정책 차이를 분석해 단일 소스의 플랫폼 경계를 설계하고, 좌석 없는 전시 상품부터 적용하는 전환 순서를 정했습니다. 좌석 데이터는 DocumentDB로 분리하고, Stored Procedure에 있던 비즈니스 로직은 Java·Kotlin 애플리케이션 계층으로 이동했습니다. 결제 완료 이후 주문 생성에는 Kafka 이벤트를 적용했습니다. 통합 결과 동일한 요구사항의 개발·반영 대상이 11개 시스템에서 1개 서비스로 줄었습니다. 2026-09-22 기준 공연·전시·스포츠를 포함한 전체 티켓팅 판매 상품의 약 95%가 신규 플랫폼에서 판매되고 있습니다.

대형 공연의 상품 상세 페이지에서는 여러 백엔드 API를 동기식으로 호출해 데이터를 조합하는 구조가 대용량 트래픽에서 병목이 되었습니다. 선예매 인증 정보는 실시간 조회를 유지하고 공연정보·캐스팅 등 메타데이터만 캐시하도록 최신성 요구를 분리했습니다. 평시 TTL은 5분, 대형 공연 판매 직전과 판매 중에는 1시간으로 운영하고 상품 오픈 시간에 맞춰 자동 적용했습니다. Spring MVC·JDK 11 환경에서 CompletableFuture와 allOf를 사용해 다수의 호출을 비동기 처리하고 결과를 조합했습니다. PDP 노출용 데이터 조회 API의 대용량 트래픽 유입 시 평균 응답시간을 3~5초에서 1초 이내로 단축했습니다.

AI를 개발 프로세스와 조직의 실행 체계에 적용한 경험

AI가 프로젝트의 개발 기준에 따라 구현하고 검증하도록 개발 절차를 구성했습니다. 신규 프로젝트는 PRD 분석에서 시작해 Technical Spec·ADR, WBS·CPM, Markdown Task를 작성하고, 구현·리뷰·QA가 같은 기준을 참조하도록 프로젝트별 Harness와 Orchestrator를 구성했습니다. 분석·설계·실행 계획 문서는 직접 검수하고, 구현·리뷰·QA는 자동 수행하도록 역할을 나누었습니다. 수행 Report는 승인 자료가 아니라 사후 점검 자료로 사용했으며, 문제가 발견되면 이전 단계의 산출물을 다시 보완하는 Workflow를 실행했습니다. 작업이 끝난 뒤에는 Harness 자체의 개선사항을 찾아 Feedback Loop로 연결했습니다.

제휴 API 연동에서는 API 명세·Mapping Table·Test Guide를 정형화하고, 제휴사별 차이는 Adapter가 담당하도록 했습니다. 내부 서비스는 SDK Connector의 공통 인터페이스를 사용하게 해 AI가 구현할 책임 범위도 명확히 제한했습니다. 주문 영역에서 개발해야 하는 서비스는 3~4개에서 1개로 줄었고, 기존 2~3명이 맡던 개발을 1인이 수행할 수 있도록 바꾸었습니다. 제휴사 1곳의 설계 착수부터 QA 완료까지의 기간은 약 2개월에서 약 2주로 단축했습니다.

개발 실장으로서는 Jira·GitHub·Slack·Confluence에 흩어진 정보를 AI Agent와 직접 개발한 앱으로 분석했습니다. Jira Label을 이용해 업무 유형과 구성원별 리소스 투입 현황을 파악하고, GitHub PR·리뷰 활동과 Slack·Confluence의 업무 커뮤니케이션을 함께 분석했습니다. 결과는 Daily·Weekly HTML Report로 만들어 조직에 공유했고, Agent는 매주 월요일 오전 8시에 실행하도록 구성했습니다.

또한 코드 저장소와 관련 문서, AWS CLI로 분석한 운영 토폴로지를 서비스 카탈로그로 정리했습니다. 문서가 남아 있지 않은 프로젝트는 코드를 분석 근거로 삼았습니다. Markdown을 기준 원본으로 관리하고 GitHub Pages로 조직에 공유해 서비스의 용도·기술 스택·배포 파이프라인·구조를 확인할 수 있도록 했습니다. 필요할 때 AI에 재분석을 요청해 카탈로그를 갱신했습니다.

함께 더 나은 구조를 만드는 방식

저는 특정 기술을 도입하는 것보다 문제의 책임 경계를 분명히 하고, 그 경계가 코드와 운영에 유지되도록 만드는 일을 중요하게 생각합니다. 설계 단계에서는 업무 규칙과 변경 특성을 확인하고, 구현 단계에서는 핵심 코드를 직접 다루며, 리뷰와 QA에서는 처음 정한 기준이 결과물에 반영되었는지 확인합니다. 팀이 같은 방식으로 실행할 수 있도록 문서·공통 모듈·리뷰 기준을 남기고, 운영 결과를 다시 다음 설계에 반영합니다.

다양한 도메인에서 시스템을 현대화하고, 설계한 구조를 직접 구현·전환해 왔습니다. 이 경험과 AI를 개발 체계에 적용한 경험을 바탕으로 제품과 플랫폼을 안정적으로 개선하는 데 기여하겠습니다.
