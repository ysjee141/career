1. 티켓팅 통합: 공통 기능과 정책 차이를 분리하다

놀유니버스 및 관계사 · 2023.09–2024.08 · 아키텍트·TF 리더 · 기획·개발 7명

문제와 제약

디바이스·장르·채널·언어에 따라 11개 시스템이 나뉘어 있었습니다. 기능은 비슷했지만 소스와 운영환경이 달라 동일 요구사항을 반복 구현했습니다. Classic ASP·.NET Framework·Stored Procedure에 축적된 업무 규칙과 단일 대형 MS-SQL 의존성도 전환 범위에 포함되었습니다.

티켓 판매를 유지하면서 좌석·결제·주문의 높은 데이터 정합성 요구를 다뤄야 했습니다. 채널별 정책과 상품 예외가 누적된 상태에서 전체 시스템을 한 번에 바꾸기 어려웠습니다.

판단과 실행

공통 기능은 통합하고 정책 차이는 명시했습니다. 시스템별 기능과 차이를 분석하고, 반복 구현하던 공통 기능을 단일 소스의 플랫폼으로 통합했습니다. 채널·디바이스별 차이는 설정과 정책으로 처리했습니다.

전환 순서를 아키텍처의 일부로 다뤘습니다. 좌석 없는 전시 상품부터 적용하고 상품·채널별로 범위를 확대했습니다. 프로덕트 조직과 어떤 상품을 먼저 옮기고 신구 시스템을 어떻게 병행할지 결정했습니다.

부하와 변경 특성이 다른 영역의 책임을 분리했습니다. 좌석 데이터는 DocumentDB와 캐시로 분리하고, Stored Procedure의 비즈니스 로직은 Java·Kotlin 애플리케이션으로 이동했습니다. 결제 완료 이후 주문 생성은 Kafka 이벤트로 분리했습니다.

상품·채널 변형단일 소스와 설정·정책동일 기능의 반복 구현 제거
좌석 데이터DocumentDB·캐시집중되는 읽기·쓰기 부하와 대형 DB 의존성 완화

주문 후처리결제 완료 → Kafka → 주문 생성처리 책임과 장애 영향 분리
서비스 운영AWS ECS 기반 독립 배포서비스별 변경·확장 가능

본인 책임과 프로젝트 결과

공통 기능·차이 분석, 서비스 경계, 데이터 저장 방식과 전환 순서를 설계했습니다. 프로덕트 조직과 이행 범위를 조율하고 핵심 구현·코드 리뷰에 참여했습니다.

프로젝트는 11개 시스템을 하나의 플랫폼으로 통합했습니다. 2026-09-22 기준, 공연·전시·스포츠를 포함한 전체 티켓팅 판매 상품의 약 95%가 신규 플랫폼에서 판매되고 있습니다. 기존에는 동일 요구사항을 11개 시스템에 각각 개발·반영해야 했지만, 단일 소스로 통합한 뒤에는 1개 서비스만 변경하도록 개발 범위를 줄였습니다. 개별 서비스 배포는 약 1~2분, 전체 컨테이너 교체는 약 5분으로 개선되었습니다.

2. PDP·BFF 현대화: 요청 경로와 데이터 책임을 바꾸다

놀유니버스 · 2022.04–2024.10 · FE개발팀장 · 조직 5명

문제와 진단

React 정적 자산과 Java API가 같은 WAS에서 제공되고 있었습니다. 여러 EC2의 Docker 컨테이너를 개별 운영했으며, 배포는 Shell Script에 의존했습니다. 상품 상세 페이지는 티켓 대기열의 보호를 받지 않아 대형 공연 판매 시 트래픽이 직접 유입되었습니다.

정적 요청도 WAS를 통과하고, BFF는 API를 단순 전달하며 대형 레거시 DB를 조회했습니다. 애플리케이션·데이터 접근·운영환경을 함께 개선해야 하는 상황이었습니다.

Spring MVC·JDK 11 기반의 PDP 노출용 데이터 조회 API에서는 여러 백엔드 API와 직접 통신해 FE에 필요한 데이터를 조합했습니다. 대용량 트래픽에서 백엔드 호출이 동시에 증가하고, 동기식 처리로 지연이 누적되었습니다.

판단과 실행

관점변경해결하려는 문제
요청 경로정적 자산을 CloudFront·S3로 분리API 서버가 정적 요청까지 처리하던 부담
화면별 데이터조합·가공을 담당하는 BFF 설계단순 API 전달 구조
데이터 접근변경 적은 데이터 사전 정제·캐시요청마다 발생하는 레거시 DB 접근
조회 캐시선예매 인증 정보는 실시간 조회, 공연·캐스팅은 캐시데이터별 최신성 요구와 반복 조회 부하
API 호출CompletableFuture로 비동기 호출, allOf로 완료 대기 후 결과 조합대용량 트래픽에서 누적되는 동기식 처리 지연
JVM불필요한 객체 생성·GC 부담 개선애플리케이션 내부 처리 부담
운영환경ECS·Auto Scaling으로 전환EC2별 수동 컨테이너 운영

예매에 필요한 최신성과 메타데이터의 변경 특성을 구분했습니다. 선예매 인증 직후 바로 예매해야 하므로 인증 정보는 캐시하지 않고 실시간 조회했습니다. 공연정보·캐스팅은 메타데이터로 분류해 캐시했습니다.

데이터·운영 상황조회·캐시 정책판단 근거
선예매 인증 정보실시간 조회 유지인증 직후 예매에 반영 필요
평시 공연·캐스팅 정보TTL 5분상품 정보 변경 가능
대형 공연 판매 직전·판매 중 메타데이터TTL 1시간해당 구간에는 상품 정보가 변경되지 않으며 트래픽 대응 필요

TTL 정책은 상품 오픈 시간에 맞춰 자동 적용하도록 구성했습니다. 이를 통해 실시간으로 확인해야 하는 정보와 캐시로 반복 조회를 줄일 수 있는 정보를 구분했습니다.

Spring MVC·JDK 11 환경에서 CompletableFuture로 다수의 백엔드 호출을 비동기화했습니다. CompletableFuture.allOf로 호출 완료를 기다린 뒤 각 결과를 조합해 PDP 조회 응답을 만들었습니다.

공통 BFF 구조와 핵심 구현을 직접 수행했습니다. 팀에는 공통 모듈과 리뷰 기준을 먼저 제공하고, 구성원별 경험에 맞춰 Java·Spring 업무를 배분했습니다. 새로운 구조를 팀이 개발·운영할 수 있도록 역할 전환까지 함께 진행했습니다.

결과

PDP 노출용 데이터 조회 API의 대용량 트래픽 유입 시 평균 API 응답시간을 3~5초에서 1초 이내로 개선했습니다. 플랫폼 개선을 통해 대형 공연 판매 시 반복되던 PDP 장애도 해소했습니다. 프론트엔드 중심의 5명 팀은 전원이 React와 Java·Spring BFF 개발·운영에 참여하는 형태로 바뀌었습니다.

3. 웹메일 제품화: 병목이 발생한 계층에서 해결하다

코비젼 · 2018.11–2019.12 · 기술연구소 연구4팀 팀장 · 조직 6명

문제와 판단

외부 SI로 개발된 웹메일은 목록 조회 API의 지연으로 납품이 어려웠습니다. 메일이 적으면 1~2초 내 응답했지만, 메일 수가 늘어날수록 지연이 증가해 약 100개일 때 약 30초가 걸렸습니다. Java IMAP 라이브러리가 Postfix·Dovecot과 직접 통신하면서 내부 동기화와 순차 처리로 데이터가 많아질수록 지연이 커졌습니다.

웹 애플리케이션에서 호출 방식을 조정하는 데 그치지 않고, 메일 서버 내부에서 필요한 데이터를 추출해 조회하기 좋은 형태로 제공하는 구조를 선택했습니다.

본인 수행

  • Dovecot Plugin Interface를 활용하는 C 플러그인을 개발하고 필요한 데이터를 별도 DB에 적재했습니다.
  • 내부 API를 구성해 웹 애플리케이션이 조회용 DB에 직접 접근하지 않도록 했습니다.
  • 대량 데이터 조회에 병렬 처리를 적용하고 발송은 메시지 큐 기반 비동기 처리로 분리했습니다.

결과와 설계 범위

개선 전에는 메일 약 100개에서 목록 조회 API 응답에 약 30초가 걸렸습니다. 개선 후 측정에서는 메일 수량에 관계없이 1초 이내로 응답했습니다. 제품은 약 3개 고객사에 적용되었습니다. 병목이 발생한 메일 서버 계층까지 구현 범위를 확장해 제품화의 장애물을 해결했습니다.

프론트엔드는 기존 그룹웨어와의 관계를 고려해 jQuery를 유지했습니다. 무작위로 적용된 jQuery UI 구조를 페이지별 모듈 선언과 필요한 모듈의 pre-load 방식으로 정리하고, 모듈 기준의 trigger·function 바인딩 규칙을 정의해 전면 교체 없이 구조를 개선했습니다. 이 개발 방식을 팀에 전파해 프론트엔드 유지보수 기준으로 사용했습니다.

개발 Harness: 프로젝트 상태에 따라 진입 절차를 구분

신규 프로젝트는 PRD 분석에서 시작했습니다. 프로젝트별 Harness를 구성하고 Technical Spec·ADR을 작성했습니다. WBS와 임계 경로(CPM) 분석을 바탕으로 실제 실행할 Task를 Markdown으로 정리했습니다.

구현의 기준과 실행 결과를 서로 다른 시점에 점검했습니다. 분석·설계·WBS·CPM·Task 문서는 도출 후 직접 검수했습니다. 이후 구현은 Implementer, 검증은 별도의 리뷰 Sub-agent가 맡도록 구성하고 구현·리뷰·QA를 자동 수행했습니다.

구분수행 주체와 방식
구현 기준 검수분석·설계·실행 계획 문서를 직접 검수
단계별 실행·리뷰Orchestrator가 진행을 조율하고 문제 발견 시 이전 단계로 복귀
결과 사후 점검수행 Report를 직접 확인하고 문제가 있으면 작업을 재요청
Harness 개선작업 완료 후 Harness의 개선사항을 도출하고 개선 작업으로 연결

Report는 실행 후 점검 자료로 사용했습니다. 사후 점검에서 발견한 문제는 Harness Workflow를 다시 수행해 보완했습니다. 단계별 리뷰에 따른 재작업과 함께, 작업 종료 후 Harness 자체를 개선하는 Feedback Loop도 구성했습니다.

기존 프로젝트는 구조 분석에서 시작했습니다. AI 도입 이전에 개발한 프로젝트를 분석해 Harness를 구축하고, QA·리뷰를 위한 Skill과 Agent를 구성했습니다. 기술부채를 주간 단위로 분석해 개선 과제를 도출하는 Agent도 구축했습니다.

신규·기존 프로젝트는 진입 분석을 구분하되 Harness의 운영 구조는 동일하게 적용했습니다. 두 경우 모두 Development Context에 아키텍처 원칙을 명시했습니다. AI가 프로젝트별 기준을 참조하도록 하고 구현과 리뷰의 역할을 분리해 균일한 품질로 개발할 수 있는 환경을 구성했습니다.

업무 분석 Agent·앱: 구성원의 활동을 실 전체 업무 현황으로 정리

개발 실장으로서 업무와 리소스 투입 현황을 파악하기 위해 여러 도구의 정보를 분석했습니다. 도구별 분석 대상과 이를 통해 확인할 내용을 구분했습니다.

분석 대상파악한 내용
Jira 업무·Label구성원별 업무 현황, 업무 유형과 리소스 투입 현황
GitHub PR·리뷰구성원이 수행한 작업과 리뷰 활동
Slack·Confluence구성원들의 업무와 관련 커뮤니케이션

Jira Label로 업무 유형을 분류해 구성원별 투입 현황과 실 전체 업무 비중을 분석했습니다. 결과는 Daily·Weekly HTML 리포트로 생성해 조직에 공유했습니다.

AI Agent는 매주 월요일 오전 8시에 실행하도록 구성했습니다. 같은 분석·리포트 기능을 가진 앱도 직접 개발해 사용했습니다. 여러 도구에 분산된 정보를 개발실의 업무 파악과 조직 내 공유에 활용했습니다.

서비스 카탈로그: 코드·문서·운영 환경을 함께 분석

AI에게 코드 저장소와 관련 문서를 제공해 분석하도록 했습니다. 문서 없이 코드만 남은 프로젝트는 코드를 근거로 프로젝트의 용도와 구조를 파악했습니다.

분석 대상문서화한 내용
코드 저장소·관련 문서프로젝트의 용도, 기술 스택, 배포 파이프라인, 서비스 구조
운영 중인 AWS 환경CLI를 통한 토폴로지 분석과 시각화

분석 결과를 서비스 카탈로그로 제작하고 조직에 공유했습니다. Markdown을 기준 원본(Source of Truth)으로 관리하고 GitHub Pages로 제공했습니다. 필요할 때 직접 AI에 재분석을 요청해 카탈로그를 갱신했습니다.

Spec Driven Development 적용 사례: 제휴 연동

제휴 API 연동은 앞서 설명한 Harness 운영 구조를 적용한 사례입니다. 구현 기준 문서는 직접 검수하고, 구현·리뷰·QA는 자동 수행했습니다. Orchestrator가 단계별 리뷰와 이전 단계 복귀를 관리하고, 수행 Report는 사후 점검에 활용했습니다.

제휴사 1곳을 연동할 때 주문 영역에서 3~4개 서비스를 개발해야 했고, 개발자 2~3명이 필요했습니다. 서로 다른 규격을 개별 서비스가 처리하는 구조에서는 연동 내부 로직의 변경도 여러 서비스에 영향을 줄 수 있었습니다.

제휴사별 차이를 Adapter가 담당하고 내부 서비스는 SDK Connector의 공통 인터페이스를 사용하도록 설계했습니다. AI가 반복 구현할 범위도 이 책임 경계에 맞춰 제한했습니다.

연동 구조와 개발 기준

flowchart LR S[내부 서비스] --> C[SDK Connector] C --> A[제휴사별 Adapter] A --> P[제휴사 API]

내부 서비스는 Connector 인터페이스를 사용하고, 외부 API 차이는 Adapter에서 처리합니다. 이 도식은 연동 책임을 나타내며 배포 단위를 의미하지 않습니다.

기준정의한 내용
API 명세제휴 규격을 정해진 형식으로 기록
Mapping Table내부 모델과 외부 응답의 변환 기준
Adapter 범위AI가 구현할 책임과 변경 범위
Test Guide연동 후 확인할 검증 기준
아키텍처·리뷰구현 원칙과 단계별 검토·재작업 절차

제휴 연동 결과

연동 구조와 명세를 표준화해 동일한 제휴 기능을 더 적은 개발 대상 서비스와 인원으로 구현할 수 있도록 바꿨습니다.

비교 항목기존변경 후
주문 영역의 개발 대상 서비스3~4개1개
주문 영역의 개발 인원2~3명1인 개발 가능
제휴사 1곳의 설계 착수~QA 완료 기간약 2개월약 2주

개발하는 기능 범위는 동일하며, 해당 기능을 연동하기 위해 수정·구현해야 하는 서비스 범위를 줄였습니다. AI 활용을 개별 코드 생성에 머물게 하지 않고, 설계 책임과 검증 기준 안에서 반복 개발하는 방식으로 적용했습니다.

설계를 팀의 실행으로 연결하는 방식

프로젝트에서는 구조 설계와 핵심 구현을 함께 맡고, 공통 모듈·코드 리뷰·문서로 의사결정 기준을 공유했습니다. 엔터주문실 실장으로 최대 12명 규모의 조직을 운영하면서 사업 과제와 기술부채의 우선순위도 조정했습니다. 기술 변경이 필요한 이유를 운영 부담과 장애 위험으로 설명하고, 팀이 지속적으로 변경할 수 있는 구조와 실행 기준을 만드는 데 집중했습니다.
