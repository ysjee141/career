티켓팅 주문 플랫폼 통합 | 아키텍트·TF 리더 | 2023.09–2024.08

디바이스·장르·채널·언어별 11개 시스템에 공통 기능이 반복되고 있었습니다. 같은 요구사항을 여러 소스에 반영해야 했고, 판매를 중단하지 않은 상태에서 상품별로 전환해야 했습니다.

제가 맡은 일은 팀이 구현할 플랫폼의 경계와 전환 순서를 정하는 일이었습니다.

  • 공통 기능과 정책 차이를 분석하고, 채널·디바이스 차이는 설정과 정책으로 처리하는 단일 플랫폼 경계를 설계했습니다.
  • 좌석 없는 전시 상품부터 전환하는 순서를 정하고 프로덕트 조직과 상품별 적용 범위와 기존·신규 시스템 병행 방식을 조율했습니다.
  • 좌석 데이터를 DocumentDB로 분리하고 Stored Procedure의 비즈니스 로직을 Java·Kotlin으로 이동했습니다. 결제 완료 후 주문 생성에는 Kafka 이벤트를 적용했습니다.
  • 핵심 구현과 리뷰에 참여하고 Next.js·React·Java·Kotlin·AWS ECS 기반 서비스의 공통 기준을 정리했습니다.

그 결과 동일 요구사항의 개발·반영 대상은 11개 시스템에서 1개 서비스로 줄었습니다. 2026-09-22 기준 공연·전시·스포츠를 포함한 전체 티켓팅 판매 상품의 약 95%가 신규 플랫폼에서 판매되고 있습니다.

PDP·BFF·운영환경 현대화 | FE개발팀장 | 2022.04–2024.10

대형 공연 판매 때 상품 상세 페이지 장애가 반복되었습니다. React 정적 파일과 Java API가 같은 WAS에서 제공되고, EC2별 Docker 컨테이너를 Shell Script로 배포하는 구조였습니다.

  • 정적 자산을 CloudFront·S3로 분리하고 EC2 기반 운영을 ECS·Auto Scaling으로 전환했습니다.
  • 선예매 인증 정보는 실시간 조회를 유지하고 공연정보·캐스팅 등 메타데이터에는 평시 5분, 대형 공연 판매 직전·판매 중 1시간의 TTL을 적용했습니다. 상품 오픈 시간에 맞춰 정책이 자동 동작하도록 구성했습니다.
  • Spring MVC·JDK 11 환경에서 CompletableFuture와 allOf를 사용해 여러 백엔드 API를 비동기 호출하고 프론트엔드용 응답을 조합했습니다.
  • 공통 모듈과 리뷰 기준을 정리하고 구성원에게 업무를 단계적으로 배분했습니다.

PDP 노출용 데이터 조회 API의 대용량 트래픽 유입 시 평균 API 응답시간을 3~5초에서 1초 이내로 단축했습니다. 기술 변경을 팀의 공통 구조와 업무 배분으로 연결한 사례입니다.

AI 기반 개발·업무 분석·지식 관리

프로젝트별 개발 원칙을 문서화하고, AI가 그 기준에 따라 구현·검증하도록 개발 절차를 구성했습니다.

  • 신규 프로젝트는 PRD 분석 → Technical Spec·ADR → WBS·CPM·Task → 구현 → 리뷰·QA → Report → Harness 개선의 흐름으로 운영했습니다. 분석·설계·계획 문서는 직접 검수했습니다. 구현·리뷰·QA는 Agent가 자동 수행하고, Orchestrator가 단계별 리뷰와 이전 단계로의 복귀를 관리하도록 구성했습니다. 수행 Report를 사후 점검해 재작업을 요청했습니다.
  • 기존 프로젝트는 코드와 문서를 분석해 Harness와 Development Context를 구성하고, 기술부채를 주간 단위로 분석하는 Agent와 QA·리뷰 Skill을 적용했습니다.
  • Jira·GitHub·Slack·Confluence를 분석하는 Agent와 앱을 구축해 구성원별 업무·리소스, PR·리뷰, 업무 커뮤니케이션과 실 전체 업무 비중을 파악했습니다. 분석 결과를 조직의 업무 방향과 리소스 투입 현황을 관리하는 자료로 활용하고 Daily·Weekly HTML Report로 공유했습니다.
  • 코드 저장소·문서·AWS CLI 분석을 바탕으로 서비스 카탈로그를 만들고 Markdown을 기준 원본으로 GitHub Pages에 공유했습니다. 필요할 때 AI에 재분석을 요청해 갱신했습니다.
