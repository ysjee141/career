기술을 좋아하고, 팀이 실제로 실행하는 구조를 만드는 리더

저는 개발과 기술을 좋아합니다. 새로운 기술이 나오면 개념을 읽는 데서 멈추지 않고 PoC나 토이 프로젝트로 직접 적용해 보며, 실제로 동작하는 구조와 아직 해결되지 않은 한계를 확인합니다. 아키텍처 서적과 실무 사례를 통해 꾸준히 학습하고, 배운 원칙이 현재 시스템의 문제를 해결하는지 검토한 뒤 팀의 개발 방식과 구조에 적용해 왔습니다.

개인 프로젝트에서도 AI를 활용해 앱을 개발하며 새로운 기술을 직접 적용해 봅니다. 배운 기술로 동작하는 결과물을 만드는 과정에서 즐거움을 느낍니다. 실무에서는 프로젝트별 개발 Harness를 구축하고, 구현·리뷰·QA 자동화와 결과의 사후 점검을 개발 절차에 적용했습니다.

기술 방향을 실행 가능한 우선순위로 바꾸는 리더

저는 리더의 역할을 기술 결정을 내리는 데서 끝내지 않습니다. 사업이 멈추지 않아야 하는 제약과 팀이 지속적으로 변경해야 하는 현실을 함께 보고, 무엇을 먼저 바꾸고 어디까지 바꿀지 정리하는 일이라고 생각합니다.

놀유니버스에서는 엔터주문실 실장으로 주문 영역의 기술 방향과 운영 안정성을 담당했습니다. 최대 12명 규모 조직에서 대기열·인증 게이트·좌석 선택·주문·결제·예매 완료까지 이어지는 흐름을 살피고, 사업 과제와 기술부채의 우선순위를 조정했습니다.

11개로 분리되어 있던 티켓팅 시스템을 통합할 때는 한 번에 전환하지 않았습니다. 공통 기능과 정책 차이를 구분하고, 좌석 없는 전시 상품부터 전환하는 순서를 정했습니다. 프로덕트 조직과 상품별 적용 범위를 조율하고, 팀이 구현할 서비스 경계와 데이터 이동 방식을 설계했습니다. 통합 결과 동일 요구사항의 개발·반영 대상은 11개 시스템에서 1개 서비스로 줄었습니다. 2026-09-22 기준 공연·전시·스포츠를 포함한 전체 티켓팅 판매 상품의 약 95%가 신규 플랫폼에서 판매되고 있습니다.

팀이 성장할 수 있는 실행 체계를 만드는 리더

좋은 개발 방식은 개인의 경험에 머물지 않고 팀이 반복해서 사용할 수 있어야 합니다. 저는 공통 모듈, 리뷰 기준, 문서와 자동화 도구를 통해 판단의 기준을 공유하고, 구성원이 새로운 영역을 맡을 수 있도록 업무를 단계적으로 배분해 왔습니다.

프론트엔드 중심으로 출발한 팀에는 React와 Java·Spring BFF를 함께 개발할 수 있는 공통 구조와 리뷰 기준을 제공했습니다. 신규 프로젝트에서는 분석·설계·실행 계획 문서를 직접 검수했습니다. 구현·리뷰·QA는 Agent가 자동 수행하고, Orchestrator가 단계별 리뷰와 이전 단계로의 복귀를 관리하도록 구성했습니다. 수행 Report를 사후 점검하고, 문제가 있으면 다시 작업을 요청했습니다.

조직 전체가 같은 기준으로 실행할 수 있도록 사내 GitHub 브랜치 전략과 CI/CD 표준도 정의했습니다. 설계 리뷰에서 기술 방향과 구현 기준을 확인하고, 구성원과 1:1 면담을 진행해 업무 수행을 코칭했습니다. 구성원의 경험과 성장 방향에 맞춰 새로운 기술과 책임을 맡도록 업무를 배분하고, 리뷰와 피드백으로 다음 실행을 지원했습니다.

조직 운영에는 Jira·GitHub·Slack·Confluence를 분석하는 Agent와 직접 개발한 업무 분석 앱을 활용했습니다. 구성원별 업무와 리소스 투입, PR·리뷰 활동, 실 전체 업무 비중을 파악했습니다. 분석 결과를 업무 방향과 리소스 배분을 판단하는 자료로 활용하고, Daily·Weekly HTML Report로 조직에 공유했습니다.

서비스 지식을 공유하기 위해 AI로 코드·관련 문서·AWS 운영 구성을 분석해 서비스 카탈로그를 만들었습니다. Markdown을 기준 원본으로 관리하고 GitHub Pages로 조직에 공유했으며, 필요할 때 AI에 재분석을 요청해 갱신했습니다.

운영 문제를 구조적 개선으로 연결하다

대형 공연의 PDP 장애를 개선할 때도 특정 코드만 고치는 방식으로 끝내지 않았습니다. 정적 자산을 CloudFront·S3로 분리하고 EC2 기반 서비스를 ECS·Auto Scaling으로 전환했습니다. 선예매 인증 정보는 실시간성을 유지하고 메타데이터는 변경 빈도에 맞춰 캐시했으며, 여러 백엔드 API 호출은 CompletableFuture로 비동기 처리했습니다. PDP 노출용 데이터 조회 API의 대용량 트래픽 유입 시 평균 응답시간을 3~5초에서 1초 이내로 단축했습니다.

이 경험은 팀에게도 같은 질문을 하게 합니다. 현재 장애의 원인이 어느 계층에 있는지, 구조를 바꾸면 운영과 개발 방식이 어떻게 달라지는지, 변경을 팀이 지속할 수 있는지를 함께 보자는 것입니다. 저는 필요한 영역은 직접 구현하고, 결정의 근거와 실행 기준은 문서와 리뷰로 남기는 방식으로 일합니다.

함께 더 나은 실행 방식을 만드는 리더

저는 다양한 도메인과 기술에 빠르게 적응하고, 그 경험을 팀의 공통 자산으로 바꾸는 리더입니다. 팀의 현재 역량과 제품의 제약을 기준으로 기술 방향을 정하고, 구성원이 성장하면서 더 넓은 책임을 맡을 수 있도록 구조와 업무를 설계합니다.

개발을 좋아하는 사람으로서 기술의 가능성을 직접 확인하고, 리더로서 그 가능성이 제품과 조직의 결과로 이어지게 만들고 싶습니다. 운영 중인 복잡한 서비스를 안정적으로 변화시키고, 팀이 스스로 더 나은 개발 방식을 만들어 갈 수 있는 환경을 만드는 데 기여하겠습니다.
